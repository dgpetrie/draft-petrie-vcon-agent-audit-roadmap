   vCon for AI Agent Conversations: Requirements, Gaps and Extension
                                Roadmap
              draft-petrie-vcon-agent-audit-roadmap-latest

Abstract

   AI agents converse with people, other agents and tools.  There is a
   growing need to capture these conversations for audit, compliance and
   review.  This document sorts the requirements for capturing agent
   conversations into those that fit vCon, those better met by plain
   logging and those that need other solutions.  It then identifies the
   gaps in vCon and proposes a strawman set of vCon extensions to fill
   them.  It is intended as a discussion document.

1.  Introduction

   AI agents act on behalf of people and other agents.  They exchange
   prompts and responses with people, delegate to other agents and
   invoke tools.  Several drafts define requirements for recording these
   interactions (e.g. [VACR] and [AUDIT-ARCH]).

   vCon [VCON-CORE] is a container for conversation data and the
   analysis of it.  A vCon captures the observation of a conversation
   from one or more points in the network.  An agent conversation is not
   that different from a contact center conversation in this respect.
   We do not want to solve all of this with vCon. vCon is a good fit for
   some of the requirements, but some are better met with plain logging
   and some need other solutions.

   This document:

   *  sorts the requirements into vCon, logging and other solutions

   *  identifies the gaps between the vCon requirements and [VCON-CORE]

   *  proposes a strawman break down of vCon extensions to fill the gaps

   This is a first cut and is surely incomplete.  We would like feedback
   on what is missing or should not be included.

    |      |   |       |   | Gateway |   |          |   |      |
    +------+   +-------+   +---------+   +----------+   +------+
       ^           ^            ^              ^            ^
      (1)         (2)          (3)            (4)          (5)

               (n) = example observation points

                    Figure 1: Example Observation Points

   The observation points in Figure 1 are examples, not an exhaustive
   list.  A conversation may be observed from any point in the network
   that it passes through, such as a gateway (e.g. [DMSC-PS] and
   [DMSC-GW]), a proxy or a platform.  In back end scenarios where
   communications inside a silo are less secure, ordinary network
   entities may also be observers.  Each observation may go in a single
   vCon or in separate vCons that are linked or merged later.  This is
   the same as a contact center call, which may be observed by the
   carrier, the contact center platform or both.

3.  Requirements and Split

   The requirements considered here come from two sources:

   *  REQ-1 through REQ-11 in section 2.2 of [VACR]

   *  the four record types in section 5 of [AUDIT-ARCH]

   Related work on AI logging includes [ISO-24970].  We only briefly
   summarize the requirements here, enough to jog the memory of someone
   who has read the source drafts.

   Each requirement is put into one or more of the following categories:

   *  vCon - the conversation and the analysis of it

   *  Logging - system and operational events

   *  Other Solutions - existing or other IETF work

   Some requirements are split across categories.

   The agent protocols themselves (e.g. [MCP] and those in
   [AGENTIC-REQS]) are not candidates for capture in vCon.  The data
   exchanged over them, and the results of them that bear on the
   conversation (e.g. identity or the tools discovered), are candidates
   for observation and capture in vCon.

3.1.  vCon

   From [VACR]:

   *  REQ-1, REQ-4 Event Logging and Type: conversation level events
      such as session start and end and permission requests and grants

   *  REQ-3 Actor Identification: people, agents and tools as parties

   *  REQ-5 Input/Output Recording: prompts, responses, agent to agent
      messages and tool invocations and results, with reasoning traces
      as analysis

   *  REQ-7 Tamper-Evidence and Integrity: integrity of the record
      itself, signing and encryption

   *  REQ-10 Human Oversight: a reviewable and redactable record of the
      conversation

   *  REQ-11 Traceability: one vCon with one or more observation points,
      or separate vCons linked or merged later

   The same conversation observed from different points may result in
   different, duplicate or conflicting data. vCon records observations,
   it does not reconcile them.  Conflicting observations are kept, each
   attributed to its observer.  Any reconciliation can be added as an
   Analysis.

   Token usage is partially captured in vCon today, as vendor responses
   (e.g. from a LLM or transcription service) are often attached as an
   Analysis and include token counts.  A more formal definition of token
   usage would be useful to contact center as well as agent to agent and
   audit scenarios.

   From [AUDIT-ARCH]:

   *  Interaction Records: prompts, responses, approvals, refusals and
      agent to agent dialog

   *  Action Records: the agent view of a tool invocation, the tool or
      service side record is another observation point which may go in
      the same vCon, a linked vCon or a log

   *  Delegation Records: only the structure of which agent delegated to
      which subagent (i.e. Session and Session_Reference)

   *  Authorization Transition Records: only the parts requested of a
      person or agent in the conversation

3.2.  Logging

   From [VACR]:

   *  REQ-1, REQ-4 Event Logging and Type: system level events such as
      configuration and prompt changes and infrastructure events

   *  REQ-2 Timestamp: clock synchronization

   *  REQ-8 Incident Response: queries over logs and vCons

   *  REQ-9 Anomaly and Risk Detection: queries over logs and vCons

   From [AUDIT-ARCH]:

   *  Action Records: the tool or service side record, when not put in a
      vCon

   [AAT] and [OTEL-GENAI] are examples of logging formats for agents.

3.3.  Other Solutions

   From [VACR]:

   *  REQ-6 Retention Period: storage and policy

   *  REQ-7 Tamper-Evidence and Integrity: non-repudiation and
      attestation (e.g. [SCITT] and [RATS])

   From [AUDIT-ARCH]:

   *  Delegation Records: the delegated authority itself (e.g. OAuth
      tokens and WIMSE)

   *  Authorization Transition Records: token level state changes

   *  propagation of audit context (e.g. trace ID) across domains

4.  Gap Analysis

   The following compares the vCon requirements in Section 3.1 with what
   [VCON-CORE] already provides.  The gaps are filled by the strawman
   extensions in Section 5.

   *  REQ-1, REQ-4 Event Logging and Type

      -  Covered: Session start and duration, join and drop Events

      -  Gap: permission and directive requests and responses ->
         Section 5.5

   *  REQ-3 Actor Identification

      -  Covered: Party Object, including type "bot", uuid, did and
         validation

      -  Gap: agent attributes such as model, provider, framework,
         version and workload identity -> Section 5.1

      -  TODO: is the Party type "bot" sufficient, or are there kinds of
         agents that need to be distinguished beyond these attributes?

      -  Gap: tools, which are named resources rather than Parties ->
         Section 5.3

   *  REQ-5 Input/Output Recording

      -  Covered: text Dialog for prompts, responses and agent to agent
         messages

      -  Gap: structured agent to agent content that is not just text,
         audio or video -> Section 5.2

      -  Gap: tool invocations and results -> Section 5.4

      -  Gap: the tools available to an agent and their definitions ->
         Section 5.3

      -  Partial: reasoning traces can be an Analysis today, but there
         is no Analysis type for them -> Section 5.6

      -  Partial: token usage is often in an attached vendor response,
         but is not formally defined -> Section 5.7

   *  REQ-7 Tamper-Evidence and Integrity

      -  Covered: signed and encrypted forms and content_hash

      -  Gap: none

   *  REQ-10 Human Oversight

      -  Covered: redacted and amended

      -  Gap: none beyond the other gaps listed here

   *  REQ-11 Traceability

      -  Covered: Session and Session_Reference, including the AI Agent
         example in the sessions Objects Array section of [VCON-CORE]

      -  Covered: an observer can be a Party

      -  Gap: which observer captured which Dialog, Event or Analysis,
         and where it was in the network -> Section 5.9

      -  Gap: grouping or linking separate vCons, as Session_Reference
         only refers to Sessions in the same vCon -> Section 5.10

      -  Gap: correlation with audit context outside of the vCon ->
         Section 5.11

   *  General, also applies to contact centers

      -  Covered: Analysis mediatype, vendor, product and schema

      -  Gap: no standard media types for the data of common analysis
         (e.g. transcripts), making it hard to use one analysis as input
         to another -> Section 5.8

   The [AUDIT-ARCH] record types map onto the same gaps.  Interaction
   Records are covered by Dialog and Section 5.5.  The agent view of an
   Action Record is covered by Section 5.4, the tool or service side by
   Section 5.9.  The structure of Delegation Records is covered by
   Session and Session_Reference.  The conversation parts of
   Authorization Transition Records are covered by Section 5.5.
